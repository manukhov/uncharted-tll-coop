# Синхронизация анимации и оружия: точка продолжения (2026-06-29)

## Подтверждено в работающей кампании

- Настоящий узел выстрела: `PlayerFireController::Fire = 0x140E2C730`.
  `controller+0x108` содержит владельца `Player`, третий аргумент содержит
  активное оружие, второй указывает на `FireArgs`. Перехват сработал в обеих
  копиях игры.
- Значение `weapon+0x218` во всех проверенных выстрелах было нулём. Это не
  подтверждённый идентификатор оружия.
- `NetEventEmitProjectileBullet` (`ctor 0x140A45520`, `Read 0x140A45B40`,
  `Write 0x140A45C90`, `Execute 0x140A45E80`, отправка `0x140A46D70`) относится
  к сетевому режиму. В кампании перехват отправки не получил ни одного события.
- `Player` vtable[26] (`0x141BB7960`) перебирает инвентарь и не сообщает текущее
  оружие. `Player+0x218` во время проверки был пуст.
- Глобальный блок ввода `0x1466E4220` оставался нулевым во время движения и
  стрельбы Chloe. Обычный ввод кампании идёт другим путём.

## Отвергнутая передача сырой «позы»

Цепочка `Player+0x1A8 -> +0x10 -> owner`, затем `owner+0` и счётчик `owner+8=60`,
дала массив записей по 32 байта. Передача и запись массива между копиями игры не
создали анимацию.

Аппаратная точка останова поймала запись по `0x1418BBBB1` внутри функции
`0x1418BB6D0`; в стеке были возвраты `0x140EF77EE` и `0x141610755`.
Декомпиляция доказала, что функция строит таблицу эффектов: в каждой записи есть
идентификатор, два указателя и флаги. Это не матрицы и не преобразования костей.
Копировать такую таблицу между процессами нельзя. Весь опытный сетевой код этой
передачи удалён.

## Родной путь анимации

- `NetEventCharacterMove::FillAnimCmdBitStream = 0x140BC4E60` упаковывает полный
  список команд анимации: клипы, смешивание, привязки и снимки позы, иерархию
  костей и выходные команды. Максимум потока: 4096 бит, то есть 512 байт.
- Заполнение события игрока `0x140BC2970` вызывает этот узел по адресу
  `0x140BC2F8B`; заполнение события NPC `0x140BC3760` вызывает его по
  `0x140BC3959`.
- Полное заполнение игрока требует активный `NetPlayerTracker`, поэтому в кампании
  следует вызывать непосредственно `FillAnimCmdBitStream`, а не внешний узел.
- В каждом `Player` по смещению `+0x1B30` встроен `NetAnimCmdGenerator`:
  конструктор `0x1403D01B0`, деструктор `0x140A090A0`, таблица виртуальных методов
  `0x14292F368`.
- `AddSnapshot = 0x140A01E50` копирует до `0x200` байт во внутреннее хранилище.
  Входная обёртка содержит размер в `+0`, время в `+8`, указатель на данные в
  `+0x688`. Вызов для полученного движения найден по `0x140A16942`.
- Обработка: `ProcessPendingSnapshots 0x140A02820`, `ProcessSnapshot 0x140A02890`,
  `GetOldestIceSnapshot 0x140A038B0`.
- `UpdateFlagsAndWeapons = 0x140A07160` применяет флаги и оружие из родного
  снимка. Поэтому этот путь должен одновременно вернуть анимации и видимое оружие.

## Следующий опыт

1. В одной копии вызвать `0x140BC4E60` для локального `Player` с правильно
   подготовленным событием и битовым потоком.
2. Найти минимальный штатный разбор полученных битов в снимок, принимаемый
   `NetAnimCmdGenerator::AddSnapshot`.
3. Подать снимок в обработчик клона `clone+0x1B30` и проверить бег, приседание,
   прицеливание и оружие без передачи по сети.
4. Добавлять сетевую передачу только после успешной проверки внутри одной копии.
